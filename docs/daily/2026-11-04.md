## What I Learned

### Chunking

- Chunking strategies: fixed size, sentence based, paragraph based, semantic and agentic. Semantic and agentic are too advanced for v1.
- Fixed size can cut a word or sentence in half. An overlap between chunks reduces this.
- Final choice for v1: sections split by heading, packed to 1000 characters with a 150-character overlap. Code blocks are never cut.
- The embedding model only reads the chunk text, not the metadata. So the heading is added to the text of every chunk. The heading is also kept in the metadata for filtering and printing.
- The chunk structure: service, then sections (by heading), then chunks inside each section.

### Embeddings and search

- An embedding model turns a chunk into a vector (a list of numbers) that carries its meaning. The query must be embedded with the same model.
- Cosine similarity compares the angle between vectors. Chroma uses L2 by default, so cosine must be set when the collection is created.
- v1 uses semantic (vector) search. Hybrid search and a reranker are Later.
- Indexing algorithms (HNSW, IVF, LSH), caching (query, embedding, vector database and LLM response cache, Redis) and monitoring (retrieval quality, response time, error rate): names only, not studied, not needed for v1.

### ChromaDB structure

- One collection (`cdk-docs`) for all services. The service is stored in the metadata and can be used as a filter.
- Each stored record has an id, the text (document), the embedding and the metadata.
- With a persistent client, data is saved in a folder on disk.
- A query is `collection.query(query_texts, n_results, where, include)`. Chroma embeds the question with the collection's embedding function. Results come back as lists of lists, closest first.

## What I Implemented

- Chunker (`chunker.py`):
  - Splits each Markdown file into sections by heading, and each section into blocks (text or code).
  - A code block is never cut. Long text blocks go to `text_splitter` (1000 characters, 150 overlap).
  - Every chunk starts with its heading. Empty sections are removed.
  - Result: 122 chunks for Lambda (73 sections), 76 for DynamoDB (40 sections) and 93 for API Gateway (37 sections), 291 in total.
- Flattening (`store.py`): one flat list where each item has `id` (`service-section-chunk`), `text` and `metadata` (`service`, `source`, `fetched`, `header`, `section_index`, `chunk_index`).
- ChromaDB setup: a Chroma embedding function with `gemini-embedding-001` (task: retrieval document), a persistent path, the collection `cdk-docs`, and cosine similarity.
- Orchestrator: the RAG steps run in order from one command.
- Trial: embedded the first 5 chunks of each service (15 chunks in total) and queried them. The query "Give a Lambda function write access to a DynamoDB table" returned `lambda-0-0` and `lambda-0-1` (distances 0.205 and 0.223). Only 15 chunks were stored, so this tests the mechanics, not the search quality.

## Problems / Errors

### Problem 1

`text_splitter` made only 2 chunks, took the whole remainder of the text as the last piece, and later lost the end of the text.

### Cause

The slice included the overlap, so the length check almost never matched. Later, the check to stop the loop ran before the last piece was saved.

### Resolution

Move forward by `chunk_size - overlap_size`, save the piece first, then stop when a piece reaches the end of the text.

### Problem 2

Empty chunks (`""`) in the packed output, and empty sections in the final data.

### Cause

`packing` saved `temp` even when it was empty. Sections with no content were never filtered.

### Resolution

Save `temp` only if it has text. Filter out sections with an empty `content` list.

### Problem 3

The heading was glued to the text, only the first chunk had it, and a code block could lose its code fence tag.

### Cause

The heading was added to the first block inside the loop.

### Resolution

Do not change blocks inside the loop. After packing, strip each chunk and put the heading and a blank line in front of every chunk. (A stray space after the blank line was also found.)

### Problem 4

The flat list had a `break` after the first section, and one list was shared by all services.

### Cause

A debug `break` was left in, and the list lived on the object instead of inside the method.

### Resolution

Remove the `break`. Use a new list for each call.

### Problem 5

Garbled characters in some chunks (for example `â\x80\x94` for a dash).

### Cause

The page text was decoded with the wrong encoding.

### Resolution

Decode as UTF-8. Later output shows the characters correctly.

### Problem 6

A chunk of 5,002 characters (the `RootStack` example, one code block).

### Cause

Code blocks are never cut, so a long code block becomes one big chunk.

### Resolution

Kept as is for v1. The Gemini input limit per text is probably 2,048 tokens (from the Vertex AI docs, not confirmed on the Gemini API page), so check the longest chunks.

After the chunking is done, we need to convert it into an embedding vector. Why do we need to convert it into an embedding vector? A vector is in n-dimensional space. If I use a model like all-MiniLM-L6-v2, just as an example, it generates a 384 dimensional vector. This vector contains the meaning of the sentence or paragraph or whatever chunk is given. Suppose there are two chunks: we give them to the embedding model and we get the vectors. When the user gives a query, it goes to the same embedding model, which makes a vector of the query, and then it tries to find the similarity between the chunk vectors we already prepared and this query vector. Whichever is the closest will be retrieved. After the embedding model, we need to store the vectors in a database. Here we will use a vector database known as Chroma, which we can set up locally. For the search algorithm we will use cosine similarity instead of L1 or L2. Cosine similarity looks at the angle. If there are two vectors, one already stored and the second our user query, it checks the angle. If the angle is very small, it will be the top result, and if it is opposite or far away, cosine similarity will see that. We can also use dot product, L1 and L2, but cosine is much more efficient, from what I have learned. There may be different similarity algorithms, but right now we are using cosine similarity.

ChromaDB gives an index to every vector, or rather to a group of vectors. This is what I understand: in the vector database, a group of vectors that are similar to each other gets an index. When a user query comes, it is converted into a vector and checked in which index it should go, so it does not search the whole database, only that group. There are indexing algorithms like HNSW, which is widely used, IVF and LSH. I have not learned them deeply, I have just learned the names. There is also caching: query cache, embedding cache, vector database cache and LLM response cache, which is the most expensive one. We can use tools like Redis for caching.
