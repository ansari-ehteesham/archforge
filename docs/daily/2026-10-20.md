## What I Learned

### AWS CDK
- `cdk bootstrap` runs once per account per region. It creates a CloudFormation stack (default name `CDKToolkit`) with an S3 bucket and roles. Its CloudFormation exec role gets `AdministratorAccess` by default, and `--cloudformation-execution-policies` replaces that.
- `cdk init` creates the project. In `cdk.json`, the `app` key is the command that runs the app (not a Python version).
- `cdk synth` creates the CloudFormation template without calling AWS. `cdk deploy` sends it to CloudFormation. `cdk diff` shows changes first.
- Hotswap updates a Lambda directly through the service API. It is faster, causes drift, and is for development only.
- `cdk watch` uses hotswap by default and ignores changes that need a full deployment, unless `--hotswap-fallback` is set. Run it from the folder with `cdk.json`.
- In CDK v2, all stable constructs come in `aws-cdk-lib`. Only alpha modules are installed separately.
- A Lambda behind API Gateway proxy integration must return `statusCode` (integer), `body` (string) and `headers`. A malformed response gives a 502.

### AWS IAM
- A principal is whoever makes a request: IAM users, roles, federated identities, AWS accounts and AWS services.
- IAM user: permanent credentials. Group: users sharing policies. Role: temporary access that someone assumes.
- Identity-based policies attach to users, groups and roles. Resource-based policies attach to resources. Managed and inline are both kinds of identity-based policy.
- Trust policy = who may assume the role. Permission policy = what the role can do. A role needs both.
- Policy JSON: `Version` is always `2012-10-17`. Each statement has Effect, Action, Resource (an ARN), and optional Sid and Condition. `Principal` is not used in identity-based policies.
- Anything not allowed is denied by default. An explicit Deny beats any Allow.

### OIDC (GitHub to AWS)
- OIDC is the protocol. In AWS you create an IAM OIDC identity provider (URL `https://token.actions.githubusercontent.com`, audience `sts.amazonaws.com`) plus a role.
- The workflow needs `permissions: id-token: write`. It gets a JWT from GitHub and sends it to AWS STS. STS checks the provider and the role's trust policy, then returns temporary credentials (1 hour by default).
- Tokens expire on their own and are not deleted after the job.
- The trust policy must name the repo and branch. For repos created after 15 July 2026 the `sub` includes numeric owner and repo IDs: `repo:OWNER@OWNER_ID/REPO@REPO_ID:ref:refs/heads/main`.

### The deploy chain
GitHub role → assumes the toolkit's deploy role → CloudFormation builds using the toolkit's cfn-exec role (the "work permit"). The file-publishing role uploads the Lambda code to the toolkit's S3 bucket.

### Cause

### Resolution

### 2. IAM learning

I have read about IAM policies. IAM is the identity and access management system in AWS, which allows different principal entities to access services in an AWS account. A principal entity is like a person; in AWS terms it will be an IAM user or IAM role. A person can be a human being, and we can also connect it with GitHub; that is considered an IAM entity. Whenever they want to do something in an AWS account we need to give them permission by creating policies. We can attach these policies to an IAM user, IAM role, IAM group, or AWS resource: these four things. The permission policies are written in JSON format.

IAM user is access we give to a person or to GitHub or anything else, with permanent access: they have sign-in details or authentication keys, not temporary access, until we remove it. We can attach policies to them and they can access whatever services we allow. IAM group is a group of IAM users. For example, AI engineers and developers: the admin wants to give SageMaker and EC2 to the AI developers but not DynamoDB. In a group there can be four or any number of people, attached to one IAM group policy. If something is not specified in the permission policy, for example I allowed only SageMaker, that person cannot access other services; by default it works like that.

Then there is IAM role: it gives temporary access to someone. That someone can be any user, human being, or federated principal, an entity that is replicating a human, like GitHub: we will use OIDC, it is an IAM role. Then there are two kinds of policy: identity-based policy and resource-based policy. In identity-based policy there are two things: managed policy and inline policy. Managed policy is where we put the JSON document; inline policy I'm not sure about, but we do not use inline policy in resource-based policy; there we use inline policies by default.

There is one more thing, the trust policy. Whenever there is a role we need to make a trust policy, which is specific only to IAM roles. In the trust policy we define which account, user, AWS STS or federated principal can attach to / take this role. Then we attach the identity-based policy, or what I understand as the permission policy: identity-based policy and permission policy are the same in meaning, only the name is different.

In the end, the JSON format of the policy: the first key is Version, and in most cases the value is a date. Below that we write multiple statements, and each statement defines one service permission. Example: I want to give person A read and write permission on a DynamoDB table named Fox, only that table. First I write the version; because we focus only on DynamoDB there is one statement. In it: Sid, a unique identification; Effect, allow or deny, here allow; then Principal, the ARN or identification of person A, so that the policy attaches only to that person; then Resource, where I write DynamoDB and the table name, because I want that person to perform operations only on that resource; then Action, where I give read and write operations; and if there is any condition we can give it too. We can create multiple statements, but this is how one statement looks. This is what I learned about IAM roles, policies and users, and federated principal entities; I think I have a basic understanding.
