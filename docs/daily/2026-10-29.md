## What I Learned

### RAG

- RAG = Retrieval-Augmented Generation. Before the LLM answers, the system looks up relevant pieces of the docs and puts them in the prompt. The LLM itself does not retrieve anything. The code around it does.
- Why RAG here: the LLM may not know the CDK constructs, or may know an outdated version. The docs give it current information.
- Two pipelines:
  - Indexing (offline, repeatable): collect, clean, convert to Markdown, chunk, embed, store in ChromaDB. Run again when there is new data.
  - Retrieval (at runtime, on every question): embed the user query, search ChromaDB, take the top chunks, send query + chunks + prompt to the LLM.
- Chunk = a small piece of a document. Chunks are used so that only the relevant part goes to the LLM, not the whole file.
- Embedding model = a model that turns text into a list of numbers (a vector). The query must be embedded with the same model as the chunks.
- Vector database = stores the vectors with the text and metadata. ChromaDB for v1.
- Metadata (`source`, `service`, `fetched`) travels with each chunk.

### Search types

- Keyword search: matches the exact words. No embedding model.
- Semantic search: matches meaning. Uses an embedding model and a vector database.
- Vector search / similarity search: the mechanism behind semantic search (find the nearest vectors).
- Hybrid search: keyword + semantic together.
- Reranker: re-orders the top results with a second model. Not studied yet.

### Python

- `os.mkdir` creates one folder level only. `os.makedirs` creates all missing parent folders. `exist_ok=True` stops the error when the folder already exists.

### 1. Day four: fixes, front matter, rules.md and RAG study

Today I put some fixes in the code. Previously I had completed fetching the HTML files of the CDK docs, cleaning them, and converting them to Markdown, but some cleaning remained. In each CDK file there was a very big table at the end of the document. I checked the pattern and removed that table, because it was not required for version 1 of ArchForge. Then there were fixes which Claude suggested yesterday. The CRLF line endings I converted to LF. I added the conversion options when converting HTML to Markdown, with the code language set to Python, so after the three backticks it automatically writes python. That way the LLM, when it retrieves a chunk, knows it is Python code. If there is a small table, not the big one, it is made compact to optimize token usage.

While fetching the HTML there was an error case where the exception block only had a print statement. I removed it and made it raise, for example raise timeout with a message. In the `save` function in utils, previously I used `mkdirs`; now I use `makedirs` with `exist_ok=True`. The first one did not create new subdirectories: if the path had three or four folders and some were missing, it gave an error. The new one creates the missing subdirectories, and if they exist it does not throw an error because of `exist_ok=True`. By default it is false, and then an existing subdirectory throws an OS error.

One more thing: when the HTML is converted to Markdown, at the top of every Markdown file there are three metadata items, added through the code, not manually. The first is the source, the URL it came from. The second is the service: if the file is about Lambda, the service is Lambda; if API Gateway, then API Gateway. The third is fetched, the date and time on which the source was fetched.

In `rules.md` we have now defined that we use `dynamodb.Table`, not `TableV2`, and for API Gateway we use REST API instead of HTTP API, not API Gateway v2. In the Lambda section I think there is no v2 construct, so we are safe there.

Then I looked into the RAG system. I have not started coding; I only tried to understand what RAG is. The full form is Retrieval-Augmented Generation. RAG is a capability that gives the LLM a way to retrieve proper, or the latest, knowledge. In our project we want the LLM to give proper code for each service. Maybe the LLM was not trained on that data, or even if it was, it may be outdated. So we give it a new version of the documentation, and for that we use RAG.

In RAG we follow a pipeline. The first part we already did: we collected the data, cleaned it and converted it to Markdown. After that we take each Markdown file and convert it into chunks. A chunk is a piece of information; for example, one paragraph can be one chunk. Then each chunk goes to the embedding model. An embedding model is also a machine learning model which converts text into a numerical vector representation, which is called the embedding. We store the embeddings in the vector database, which in our case is ChromaDB. There are many other vector databases, like an S3 vector database, or FAISS (I'm not sure how to pronounce it). Because ChromaDB is easy to understand and work with, and this is version 1, we use only ChromaDB. This whole step can be repeated whenever there is a new data source.

Then how does the LLM get the information? That is a different pipeline. Suppose the user asks "how to connect Lambda with DynamoDB". This user query goes to the RAG through a search tool. The pipeline first embeds the query, because we stored vector representations in ChromaDB, so the input must be a vector too. Then ChromaDB searches for the nearest, most meaningful chunks and returns the top 5 or 6. This is why we use chunks: we do not want the whole document, only the specific information. The returned information is the RAG context. Then the user query plus the context goes to the LLM as a prompt; here we need some prompt engineering. The LLM gets the user query, the rules it must follow, and the actual information retrieved by the RAG, and can then give a proper answer. The retrieval part always runs at runtime: whenever the user asks a question, it goes to the RAG tool, embeds the query, searches, and so on.

About the search algorithms. The most basic one is keyword search: it tries to match the exact keyword. If I say "cancel membership", it looks for that. If I say "lambda", it searches the Lambda documentation. Then there is semantic search, which checks the meaning. Here we use the embedding model, and that is why the vector database comes into place. In the keyword search we will not use the embedding model. In the keyword search we will be using the embedding model. In the semantic search we will be using the embedding model. Then there is vector search or similarity search, which is the mechanism behind semantic search. I did not understand correctly the difference between vector search, similarity search and semantic search. Then there is hybrid search, which combines keyword search and semantic search, and there is a re-ranker, which I have not understood in detail. I will read about these search types and continue tomorrow.
